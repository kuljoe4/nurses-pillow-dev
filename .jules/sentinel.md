## 2024-10-24 - Fix IDOR and Auth Token Vulnerabilities
**Vulnerability:** The application incorrectly saved 6-digit email verification PINs into the `reset_password_token` database column, which allowed malicious actors to initiate a password reset using only the verification PIN. Additionally, `resolveUserIdentity` queried the database using untrusted client-provided emails to resolve user IDs, leading to IDOR vulnerabilities in fallback routes like favorites. Email uniqueness during registration did not use case-insensitive matching (`LOWER(email)`), allowing duplicate account creation and potential account takeovers. Finally, hardcoded mock values for Twilio SMS verification and Postmark allowed verification bypass in production environments.
**Learning:** Never reuse security tokens for different purposes (e.g., password resets vs. email verification). Never trust unauthenticated client-supplied IDs or emails to look up user context for state-mutating actions (always derive identity strictly from the JWT). Always enforce case-insensitive uniqueness at both the application and database levels for identity fields. Finally, never deploy hardcoded mock verification bypasses in production code, even for testing.
**Prevention:** Rely strictly on in-memory ephemeral stores (`pendingEmailVerifications`) for temporary verification PINs that don't need persistence. Refactor identity resolution functions to strictly enforce JWT checks and ignore unauthenticated client inputs. Add a database-level `CREATE UNIQUE INDEX ... ON users(LOWER(email))` to enforce uniqueness guarantees at the lowest level. Strip all mock bypasses from external service integrations (Twilio, Postmark) and ensure failure modes default securely to rejected requests rather than silent successes.
